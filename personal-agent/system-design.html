How the personal agent is built

It's one Node process on your Mac. It runs an AI loop, keeps everything it knows in one folder, and serves a React chat page. This page covers the 20% of the code that explains the other 80%.

01 · FIRST PRINCIPLES

An agent is four parts

Every AI agent, this one included, comes down to four parts. Everything else in the repo connects them.

1

A loop

Send the conversation to a model. If it asks for a tool, run the tool, add the result, and ask again. Stop when it simply answers.

vendor/pi-core/agent-loop.ts

2

A memory

What it keeps: every message (SQLite), what it learned (Markdown files + git), and settings and logins (private JSON).

~/.personal-agent

3

A face

How you talk to it: a React page in the browser, or the terminal. Later, WhatsApp.

apps/web · cli.ts

4

Hands

Tools that do things: edit its own memory, skills and wiki, search past chats, and call outside apps through MCP or Composio.

learning/ · mcp/ · composio/

The one sentence to rememberA conversation is a list of messages. The loop sends that list to a model with a menu of tools, runs whatever tools the model picks, and saves every message as it goes.
02 · THE WHOLE SYSTEM

The whole picture

You talk to the daemon. The daemon talks to a model, to outside tools, and to its home folder. Nothing else is involved.

how you talk to it the daemon the loop outside services disk

Say it in five sentences

If you present this to someone, this is the whole architecture:
  1. The agent is one Node process on my Mac, called the daemon. It only listens on localhost:4545.
  2. Inside it, Pi's agent loop sends the conversation to a model (ChatGPT or Claude) and runs the tools the model asks for until it answers.
  3. A React page sends actions as POST requests and gets the reply as a live SSE stream. The terminal chat calls the same code directly.
  4. Everything it keeps lives in one home folder: conversations and token costs in SQLite, what it learned in Markdown files committed to git, and logins in private JSON files.
  5. Every 10 messages, a background review rereads the conversation and decides what to remember. Each change must quote my own words.
03 · WHY IT LOOKS LIKE THIS

Five design choices that explain the code

Most of the code follows from these five choices. Learn them and the rest is easy to predict.

1 · Local only

One process on your Mac, listening only on loopback. There are no accounts, so there's no login code. The cost: never expose the port.

http/validation.ts checkOrigin

2 · It owns its history

Every message is saved as full JSON in SQLite, not left with the provider. Any model can pick up any conversation later.

sessions.ts

3 · Learning you can audit

Memory, skills, bots and the wiki are Markdown files. Each change is a git commit with its reason, so git log shows what it learned and git revert undoes it.

home.ts commit()

4 · One prompt per conversation

The system prompt is built once and never changes mid-conversation, so the provider can cache it. New memories show up in the next conversation.

conversations/prompt.ts

5 · Thin routes, state in its owner

HTTP handlers only validate and delegate. Each piece of state has one owner: the registry owns the active chat, SessionStore owns SQLite, and MemoryStore owns its files.

http/routes/*

04 · THE REPO

Two apps, one rule

A pnpm workspace with two apps. They never import each other. They only share HTTP and SSE.

apps/daemon: the brain and the server

Node 24 runs the .ts files directly, with no build step. It uses Node's built-in node:sqlite.

Dependencies: pi-ai (model providers), @modelcontextprotocol/client, typebox (schemas), yaml.

src/ · test/ (unit, journeys, emulators) · evals/

apps/web: the face

React 19, Vite, Tailwind 4, React Query, Base UI, React Router (URL only).

pnpm build writes apps/web/dist. The daemon reads that build once at startup and serves it, so a rebuild needs a restart.

src/api · src/shell · src/settings · src/mcp · src/connections · src/bots

The ruleBrowser code can't import daemon code, and the daemon can't import browser code. Biome enforces this. The web types the daemon's JSON by hand in api/wire.ts, and e2e/wire-contract.ts checks those types against the daemon's own at compile time, so the two can't drift without pnpm check failing.

05 · INSIDE THE DAEMON

The daemon, top to bottom

Each layer only calls the layers below it. A request enters at the top and the data lands at the bottom.

L1
Entry pointsserver.ts · cli.ts
Opens the runtime, wires routes and callbacks, starts listening. Shutdown stops the reply and reviews first, then closes SQLite.
L2
HTTPhttp/
validation.ts checks host, origin, JSON and schema. routes/*.ts are thin handlers. events.ts is the SSE broadcaster. static.ts serves the built page and images.
L3
Registryconversations/registry.ts
Holds exactly one active conversation for the whole server, plus starting and replying flags. It builds the snapshot every tab shows and forwards loop events to SSE.
L4
Conversationconversations/conversation.ts
Owns one Pi Agent. It builds the system prompt and tool list, saves every message to SQLite, counts toward reviews, and blocks learning writes after outside data arrives.
L5

Model ↔ tools until done. It emits events (message_end, tool_execution_start and others) that layers 3 and 4 listen to.
L6

L7
Disk~/.personal-agent
SQLite, Markdown and git, and private JSON. Set AGENT_HOME to use a different folder, which is how tests stay away from your real agent.

06 · THE HEART

The agent loop

The model can't do anything by itself. It can only ask for a tool. The loop runs the tool and asks again.

// The idea of runLoop() in vendor/pi-core/agent-loop.ts, simplified to its core
while (true) {
  const reply = await streamFn(model, { messages, tools }); // emits text_delta events as it streams
  messages.push(reply);
  const calls = reply.content.filter((part) => part.type === "toolCall");
  if (calls.length === 0) break;                            // a plain answer: done
  for (const call of calls) {                                   // toolExecution: "sequential"
    const block = await beforeToolCall(call);                   // safety hook from conversation.ts
    const result = block ? block.reason : await tool.execute(call.arguments);
    messages.push({ role: "toolResult", ...result });
  }
}

Who listens to the loop's events

Conversation

message_end saves the message to SQLite, and a model call to model_calls. turn_start and tool_execution_start count toward reviews and reset them.

conversation.ts constructor

Registry

text_delta becomes SSE {type:"text"}, tool_execution_start becomes {type:"tool"}, and a failed reply becomes {type:"error"}.

registry.ts start()

07 · FOLLOW ONE MESSAGE

One message, end to end

You type "Draft an opener for Acme" and press Enter. This is every hop. The POST returns right away, and the reply arrives over the live stream.

Solid arrows are calls. Dashed arrows are answers or events that arrive later. Steps 7 to 11 repeat for as long as the model keeps asking for tools.

Why the POST returns 202 before the replyA reply can take a minute. The POST only says "accepted". Every open tab watches the same SSE stream, so a second tab sees the reply too. The server allows one reply at a time: a second send while one runs gets 409 Still replying.

The code for steps 1 to 4 and 14

// apps/daemon/src/http/routes/chat.ts (trimmed)
"POST /messages": async (request, response) => {
  const { text } = await readJson(request, messageBody);     // ≤ 24,000 chars, schema-checked
  if (registry.replying || registry.starting) throw new RequestError(409, "Still replying…");
  registry.conversation ??= await registry.start(registry.currentBot(), true); // resume latest
  registry.replying = true;
  broadcast({ type: "user", text, session: registry.conversation.id });
  response.writeHead(202).end();                                // the browser is free now
  try {
    const { review } = await registry.conversation.send(text);  // the whole loop runs here
    if (review) registry.announce(review, registry.conversation.bot.id);
  } finally {
    registry.replying = false;
    broadcast({ type: "done" });
    broadcast({ type: "bots", bots: runtime.bots.list() });
  }
}

Two queues keep writes safe

A chat reply and a background review can both try to save at the same moment. Two simple promise chains put them in line:

Learning write queue

Each read-modify-write-commit of memory, skills, the wiki or a bot runs as one unit, one at a time. Two writers can't overwrite each other's edit.

learning/writes.ts serializeLearningWrite()

Commit queue

Git allows one writer per repo. Commits run one after another, and a failed commit unstages its files so the next commit can't pick them up.

home.ts commit()

// learning/writes.ts: the whole queue. Each operation waits for the one before it.
let writeQueue: Promise<unknown> = Promise.resolve();
export function serializeLearningWrite<T>(operation: () => Promise<T>): Promise<T> {
  const next = writeQueue.then(operation);
  writeQueue = next.catch(() => undefined);   // one failure doesn't block the line
  return next;
}
10 · THE DATABASE

The tables in sessions.db

There's one SQLite file at ~/.personal-agent/sessions.db, opened with Node's built-in node:sqlite. It has no ORM and no migration tool: the schema is a string in sessions.ts.

Every column

sessions · one row per conversation
idTEXT PKA UUID made by new Conversation()
started_atINTEGEREpoch ms
bot_idTEXTWhich bot owns it. Default 'default'. Every read is filtered by it, so bots can't see each other's chats

reviews · review progress per conversation

Marks only move forward (max(old, new)), so a review never re-learns from messages it already saw.

messages · every message, in order

session_idTEXT→ sessions.id

textTEXTOnly the text parts, for search. Empty for system and tool-only rows
messageTEXTThe full pi-ai message as JSON. Parsed back on resume

model_calls · usage and cost

provider, modelTEXTe.g. openai, gpt-6.1-sol

Three safety rails

1 · No saving after outside data

Once an outside result arrives in a turn (an app, recalled text or a wiki page), memory and skill_manage are blocked until your next message. This guards against prompt injection.

conversation.ts beforeToolCall

2 · Reviews must quote you

A background change needs at least 3 words quoted from your new messages. Wiki changes may quote outside results.

review.ts beforeToolCall

3 · Automatic means add-only

A review it starts on its own can add memories, but it can't replace or remove them, and it can't supersede a wiki claim. Only you can.

memory.ts addOnly

13 · GETTING BETTER

How it learns: the background review

After the reply, a copy of the conversation is asked what's worth keeping. It runs in the background, so you never wait for it.

1 · Trigger10 messages from you → memory review. 10 model calls → skill review. Review now → both. A save made in chat resets its counter.conversation.ts
→
2 · ForkA new Agent with the same model, messages and tool declarations (so the prompt cache still hits), but only local learning tools work.review.ts runReview()
→
3 · AskHermes's review prompt + "learn only from the new part" + the quote rule. At most 16 model calls.review-prompts.ts
→
4 · SaveEach change goes through the write queue and gets a git commit with its reason.writes.ts · home.ts
→
5 · ReportSSE learned shows what changed. Marks move forward in reviews, and costs land in model_calls as review.registry.ts announce()
Where each kind of learning goesMemory: facts true in every conversation (who you are, setup). Skills: how to do a kind of task. Wiki: knowledge about projects, people and decisions, with sources. Conversations: everything else, searchable later.

15 · WHAT IF

What happens if we build an Electron app

Very little changes. Electron is a Chromium window plus a Node process, and this app is already a web page served by a local Node server. The desktop app becomes a window pointed at http://127.0.0.1:4545.

Nothing here is built. This is how the current design would take it.

Step 1 · simplest

Electron starts the daemon

BrowserWindowloads http://127.0.0.1:4545 (the same React page)
Electron main processspawns `node apps/daemon/src/server.ts`, then SIGTERM on quit
~/.personal-agentunchanged

Good for a first version. Quitting the app stops the agent.

Step 2 · when it must run 24/7

launchd runs the daemon, Electron is a window

Electron (menu bar + window)attaches to the running daemon
launchd servicethe daemon, always on, as the PRD plans
~/.personal-agentunchanged

Needed once WhatsApp and schedules arrive. Closing the window must not stop the agent.

What stays the same and what needs care

ItemWhy
SameAll of apps/webThe window loads the same page from the same server
SameAll of apps/daemon, the HTTP/SSE contract, the home folderThe page sends Host: 127.0.0.1:4545 and is same-origin, so checkOrigin passes unchanged
SameBrowser and terminal chatThey keep working next to the app, against the same daemon
CareOne process per homeUse app.requestSingleInstanceLock(). If the port already answers, attach instead of starting a second daemon. Two daemons on one home means two writers
CareWhich Node runs the daemonIt needs Node ≥ 24.12 (it runs .ts directly and uses node:sqlite). Spawning the system Node avoids this. Running it inside Electron's own Node needs a JS bundle and a check that its Node supports both
Caregit must be installedEvery learning save runs the git CLI
CareKeep port 4545 fixedThe MCP OAuth redirect is http://127.0.0.1:4545/api/mcp/oauth/callback, and registered clients depend on it
CareSign-in pagesComposio's Connect navigates the page itself, which works in the window. Popups should go to shell.openExternal so they use your real browser
CareClean shutdownSend SIGTERM. server.ts then stops the reply and reviews, saves, and closes SQLite
CareSecurity is unchangedThere's still no login. Keep it on loopback and never load remote pages in the window
// apps/desktop/main.ts: a sketch, not in the repo (Step 1 with "attach if already running")
import { app, BrowserWindow, shell } from "electron";
import { spawn } from "node:child_process";

const URL = "http://127.0.0.1:4545";
if (!app.requestSingleInstanceLock()) app.quit();          // one process per home
const up = () => fetch(URL).then(() => true, () => false);

app.whenReady().then(async () => {
  const daemon = (await up()) ? undefined                       // already running: attach
    : spawn("node", ["apps/daemon/src/server.ts"], { stdio: "inherit" });
  while (!(await up())) await new Promise((r) => setTimeout(r, 200));

  const win = new BrowserWindow({ width: 1100, height: 760 });
  win.webContents.setWindowOpenHandler(({ url }) => { shell.openExternal(url); return { action: "deny" }; });
  await win.loadURL(URL);
  app.on("before-quit", () => daemon?.kill("SIGTERM"));      // the daemon saves, then exits
});
The option to avoidReplacing HTTP with Electron IPC. You'd rewrite live.ts and post.ts and maintain two contracts, and the browser, the HTTP journeys and the Playwright checks would no longer cover the desktop path. HTTP on loopback is already the boundary, so keep it.
